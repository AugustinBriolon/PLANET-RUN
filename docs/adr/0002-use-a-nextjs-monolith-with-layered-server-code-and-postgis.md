# 2. Use a Next.js monolith with layered server code and PostGIS

Date: 2026-09-16

## Status

Accepted

## Context

Planet Run imports a runner's Strava history, renders it on a 3D globe, and will later compute street coverage
percentages per city, department, region and country. The first milestone (sign in with Strava, import runs,
show them on the globe) is built by a single developer, so operational simplicity matters more than independent
scaling. The coverage roadmap, however, requires geospatial queries (OpenStreetMap road networks, administrative
boundaries, line length intersections) that a plain relational store cannot answer efficiently.

The development machine is an Apple Silicon Mac: the official `postgis/postgis` image publishes no `arm64`
variant.

## Decision

We will build Planet Run as a single Next.js 16 (App Router, TypeScript) application that serves both the UI and
the server-side logic, backed by PostgreSQL 17 with PostGIS 3.5 accessed through Drizzle ORM.

Server code is layered and wired in one place:

- `src/server/repositories/` — data access factories taking a `Database`, exposing narrow typed interfaces.
- `src/server/services/` — business rules (account linking, run sync, webhooks, token refresh) that depend only on
  repository and client interfaces injected as arguments.
- `src/server/services.ts` — the composition root, the only module that instantiates concrete implementations.
- `src/lib/` — pure, client-safe functions (GeoJSON conversion, stats, formatting).

Local Postgres runs in Docker Compose with the multi-arch `imresamu/postgis` image, published by a
docker-postgis maintainer. Schema changes are versioned SQL migrations generated by `drizzle-kit`.

## Options considered

### Option A — Next.js monolith + Drizzle + PostGIS (chosen)

- Pros: one deployable and one language; Server Components and Server Actions remove a hand-written API layer;
  Drizzle is lightweight, typed, and supports raw SQL for future PostGIS functions; PostGIS is the reference for
  street-coverage computations.
- Cons: long-running jobs (multi-day Strava stream backfills, OSM imports) do not fit request handlers and will
  need a separate worker process; ties the backend to the Next.js release cadence.

### Option B — Separate SPA frontend and API service (e.g. Vite + Fastify)

- Pros: independent deployment and scaling; clearer API contract for a future mobile app.
- Cons: two codebases, duplicated types or a contract-generation step, CORS and auth cookie plumbing; more
  infrastructure for no present requirement.

### Option C — Backend-as-a-service (Supabase)

- Pros: hosted Postgres with PostGIS, auth and storage out of the box.
- Cons: Strava is not a first-class auth provider; business logic split between SQL policies, edge functions and
  the app; harder to unit test services in isolation; vendor lock-in.

### Option D — Prisma instead of Drizzle

- Pros: mature migrations and tooling.
- Cons: heavier client and query engine, weaker ergonomics for raw PostGIS SQL that the coverage engine will need.

## Consequences

### Positive

- A new feature touches one repository and one `pnpm dev` process.
- Services are unit-tested with in-memory fakes because they never import the database or `fetch` directly.
- Swapping an implementation (e.g. a Garmin client, a queue-backed sync) only changes the composition root.
- PostGIS is available from day one, so the coverage milestone requires no database migration of engines.

### Negative

- Background work (full GPS stream backfill under Strava rate limits, OSM imports) will require adding a worker
  process and a job queue in a later ADR.
- `imresamu/postgis` is a community image: its availability must be re-checked when upgrading Postgres.

### Neutral

- Local database listens on port 5433 to avoid clashing with a host Postgres on 5432.
- An integration test database `planet_run_test` is created by `docker/create-test-database.sql`.
